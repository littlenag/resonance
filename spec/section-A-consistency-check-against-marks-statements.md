### Tensions found

- **T1 — "Mounted file system" versus "no mount."** Mark's restriction was first phrased around a mounted file system; he later rejected NFS mounting as too fraught. This specification keeps the substance of the restriction (the files form a standard project; graph-only information stays behind a separate API) and delivers it as a replica working tree instead of a mount (NG1, §7). **Confirm** that the restriction still applies unchanged to the replica.
- **T2 — "Graph is the source of truth" versus text files being edited directly.** Resolved in §8.1: the graph stores exact file content and is authoritative, and the working tree is its replica. Text writes are always accepted and flow into the graph. Structure is derived from that text.
- **T3 — "SQLite in the repo" versus mergeable git history.** A committed SQLite file cannot be merged by git. §8.6 keeps SQLite as the store in every option but proposes committing an operation log for anything shared. **Resolved** by Mark (row 23): a SQLite snapshot plus delta files, compacted every N (FR-026, §8.6.1).
- **T4 — "Need not be textual" versus a textual committed form.** Mark's statement is honored for the store itself (FR-060). The committed form of the edit algebra is a separate choice; text is recommended only for review in pull requests. Mark's later direction (FR-072) settles the principle: the committed format is chosen for the data model, not for git diffs. The exact delta encoding is still OQ-02.
- **T5 — Skepticism about structure versus a hypothesis that structure reduces tokens, time and developer time.** These can both be true if they refer to different kinds of structure. §12 separates code structure (arm B, expected small effect) from intent structure (arm C, the Resonance thesis). **Confirm** which kind of structure the stated hypothesis referred to, or whether it covers both.
- **T6 — "FOD is obsolete" versus agents still editing text files.** This specification lets agents keep editing files (FR-131) because generation is still strongest in text and every downstream tool consumes files, and it treats files as a projection (§2.4). **Confirm** this is an acceptable migration stance, rather than requiring agents to work only through the graph.
- **T7 — "Which port is active" versus Unix sockets.** Mark described discovery as finding which port serves a directory. FR-086 proposes Unix domain sockets instead of TCP ports, for access control and to avoid exposing a mutating service on localhost (FR-087). Discovery works the same either way: it returns an endpoint. **Confirm** sockets, or keep TCP ports with the token requirement.
- **T8 — Projected intent documents versus "everything extra hidden behind another API."** FR-121 proposes optionally projecting requirements and decisions as Markdown files in the working tree, which departs from the decided restriction in FR-015. It is opt-in and labeled as an exception. **Confirm** or drop it.
- **T9 — FR-012b "the file on disk renamed" versus P2 (nothing in the working tree but `.resonance/`).** FR-012b as written renames the conflicting disk file in place. A renamed file in the source tree can be picked up by build tools, test runners and `git add -A`, so this specification preserves the displaced version in `.resonance/local/recovery/` instead and names it in the conflict message. It also limits FR-012b to files for which the graph is authoritative, and classifies changes before treating them as conflicts, so that a `git pull` made while the daemon was off is not reported as hundreds of conflicts. **Confirm.**
- **T10 — FR-066 "reviewable on standard hosting platforms without custom tooling" versus FR-072 (no bending the data model for git).** With a binary snapshot and engine-neutral deltas, raw hosting-platform diffs are not enough to review graph changes. FR-066 now relies on a textconv driver, `resonance review` and an optional CI comment. **Confirm** that this trade-off is acceptable.
- **T11 — FR-025 [Decided] "`init` MUST add them to `.gitignore`" versus S1 AC1 ("no existing file is modified") and offline mode.** Editing the root `.gitignore` changes a tracked file that teammates see. The mechanism is changed to `.git/info/exclude` in offline mode and a new `.resonance/.gitignore` from stage 2 onward. The decided part, that local files are never committed, is unchanged. **Confirm.**
- **T12 — FR-081 (direct read-only store access) and FR-105 (read-only SQL escape hatch) versus storage encapsulation.** Both expose SQLite to callers. They are kept only as engine-specific, unstable capabilities that Resonance's own code may not use (FR-168). **Confirm**, or drop them.
- **T13 — §8.1 "the graph is authoritative for bytes" versus staged adoption.** **Resolved** by Mark (row 28): authority is per developer. The graph is authoritative for everyone who has opted in, from the moment they opt in, and git only for developers who have not. The "shadow" and "primary" developer modes are gone, and the stages are renumbered 0–3, with "files leave git" as a possible stage 4.
- **T14 — "Delta patch databases" (original FR-026 wording) versus engine-neutral operation deltas.** This specification makes deltas serialized edit-algebra operations rather than SQLite patch files (FR-164). A page- or row-level patch is tied to one engine and to one exact base snapshot. It would stop applying once trunk compacted while a branch was in flight, and would not survive a move to a graph engine. Semantic operations survive both. **Confirm.**
- **T15 — Agents gating actions versus FR-203.** **Resolved** by Mark (row 28): FR-203 now binds every developer who has opted in, at every stage. Their agent's gates and git hooks may block inconsistent operations, and only developers who have not opted in are never blocked.
- **T16 — Offline mode versus "opting in makes Resonance your source of truth".** **Resolved** by Mark (row 29). Offline is trying, not buying, and it is not opting in. The offline graph is private and derived solely from git history and the file tree, so git is authoritative and the graph follows. Offline users bear the largest divergence and the highest repair cost, in exchange for complete invisibility. In an already-shared repository, offline mode reads the committed graph as one more input and contributes nothing back, so the developer benefits from the shared graph and stays private until they consent (FR-187, confirmed by Mark).
- **T17 — "Remove" spec items versus "never delete" (FR-003, MVP-011).** The TUI's remove action retires items rather than deleting them, so links to them become reviewable instead of disappearing (FR-271). Similarly, imported items stay owned by their source documents, so the TUI opens the document rather than diverging from it (FR-272). **Confirm** both.
