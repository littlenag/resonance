## 16. Open questions

| ID | Question | Notes |
| --- | --- | --- |
| **OQ-01** | How is authored data committed to git: operation-log files (A), custom refs (B), or the SQLite file (C)? | **Resolved** by Mark: a SQLite snapshot plus delta files, compacted every N (option D, FR-026, §8.6.1). |
| **OQ-02** | Is the committed delta format text (JSON Lines) or compact binary? | Decide on fidelity and size, not git diffs (FR-072); PR review comes from tooling (FR-066). Must be engine-neutral (FR-164). |
| **OQ-03** | Which graph engine replaces SQLite, and when? Build, fork, or build on an existing one (G11)? | Mark expects to move to a real graph engine after research. SQLite stays behind the store API until then (§8.2.1); candidates are judged against the conformance suite and NFR-030–035. |
| **OQ-04** | API transport: JSON-RPC or gRPC over Unix sockets? | §8.8 |
| **OQ-05** | Is a general query language needed, and which one? | Start with fixed operations and a read-only SQL escape hatch. |
| **OQ-06** | Which languages would a code-structure parallel graph cover, if one is integrated? | Not applicable to core, which is language-agnostic and parses no code (FR-110, FR-114). |
| **OQ-07** | Windows support: when, and with which file-event API? | Not in the first release. |
| **OQ-08** | Do git worktrees share a derived-data cache? | §8.6 FR-070 |
| **OQ-09** | Is verification evidence committed, summarized, or kept local? | Proposed: full records local, latest summary committed. |
| **OQ-10** | How do code-fluent developers annotate code: graph-only, tagged comments, or both? | Proposed: graph-only, through the agent (and later the IDE plugin); agents may honor tags they read, but Resonance does not scan for them (NG6). |
| **OQ-11** | Implementation language: Scala (deep expertise, JVM cost for daemons), Rust (small, fast daemons), Go, or a mix (for example a Rust daemon with Scala tooling)? | **Resolved** by Mark: Rust (§7.1). |
| **OQ-12** | Where do projected intent documents live, and in what Markdown conventions? | FR-121 |
| **OQ-13** | Should the registry ever supervise (restart) daemons? | FR-094 |
| **OQ-14** | Is there eventually a shared, multi-user graph service, or does collaboration stay git-only? | NG3 |
| **OQ-15** | License. | Project name decided: Resonance. |
| **OQ-16** | Are folded operations ever pruned from snapshots, and how? | FR-157 needs them for mechanical repair; git history keeps the original deltas. |
| **OQ-17** | Compaction defaults: the value of N, a size trigger, how the trunk is detected, and whether the daemon compacts automatically or only CI and explicit commands do. | FR-154–FR-156 |
| **OQ-18** | Must offline mode be branch-aware from Phase 1, or is one global local graph acceptable at first? | FR-183 |
| **OQ-19** | Do files ever leave git (stage 4)? If so, file content moves into committed Resonance data, and unaware tools get files only from the projection. | §8.16, FR-064, FR-074 |
| **OQ-20** | Is path-scoped authority needed, and at what granularity (directory, glob, file)? | FR-178 |
| **OQ-21** | Which agent harnesses beyond Claude Code get first-class kits (skills, hooks), and which get only `AGENTS.md` plus MCP? | FR-214 |
| **OQ-22** | What may quiet bookkeeping write: manifests and identity operations only, or also agent-asserted links? Should a CI bot add bookkeeping commits by default at stage 3? | FR-233, FR-235, FR-236 |
| **OQ-23** | Are parallel graphs stored in Resonance's store under their own namespace, or federated from the producing tool's own store (for example Mache's)? | FR-119. Storage gives one query engine; federation avoids copying and keeps the tool independent. |
| **OQ-24** | What exactly must a producer supply for a parallel graph to become write-capable, and does any tool meet it? | FR-241. Mache was not built for this. |
| **OQ-25** | Should loaded disconnected graphs ever be shared with teammates (committed or published), or always stay local and be regenerated by each developer? | **Resolved** by Mark: local only (FR-243). |
| **OQ-26** | Should the TUI write a change to an item back into the document it came from itself, instead of leaving that to the agent through a stale `derivedFrom` link? | FR-272, FR-124. Resolved for now: the agent keeps documents in step; Resonance writes no project files for TUI edits. |
| **OQ-27** | Should changes made by agents appear in the change log, for example so that one agent learns what another changed? | FR-274 proposes people's changes only by default, with `changes.includeAgents`. |
| **OQ-28** | What should happen to intent that agents infer while building: requirements, decisions, designs and behavior that no person wrote down? Options: (A) record all of it in the graph and have agents justify why every part of the project exists, alone and as part of the whole; (B) record none of it, as noise that will never be worth anything to agent or person; (C) record some of it and discard the rest, which needs a way to choose. | A spec covers only the part of the behavior a person has had time to think through deeply. Inferred intent can matter as much as explicit intent, especially where the initial design was incomplete or missed edge cases. A risks a tight decision loop; C costs prioritizing and filtering. Agent provenance and `asserted` status (FR-134), and MVP-### items as implementation decisions the full spec leaves open, are existing precedents. |
| **OQ-29** | Should one web UI cover every repository on the machine (served next to the registry, switching between daemons), instead of one UI per daemon? | FR-286 serves one UI per daemon, on its own port. The registry already knows every daemon (FR-088), but it must not sit between a client and a daemon (FR-089). |
| **OQ-30** | Should diagnostics be kept across daemon restarts, so that what happened before a crash or an idle exit can be inspected? | FR-294 keeps them in memory for the daemon's lifetime only; the log file (FR-297) is the only record that outlives the daemon. |
| **OQ-31** | How much of the web UI can the IDE plugins reuse (IntelliJ's embedded browser, Nimbalyst's extensions), and is Nimbalyst's extension architecture mature enough for FR-143? | FR-141, FR-143. Writing the web UI in TypeScript and React keeps reuse possible; the plugins' native parts (gutter markers, navigation, FR-142) cannot come from it. |
| **OQ-32** | Should decisions, designs and constraints be placed in milestones too, or only requirements? | FR-300 places requirements only. A design or constraint that serves only later requirements could be planned with them; a decision is usually made when it is needed. |
