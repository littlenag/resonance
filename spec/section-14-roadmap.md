## 14. Roadmap  [Proposed]

| Phase | Scope | Exit criteria |
| --- | --- | --- |
| **0 — Evaluate** | §12. No Resonance code beyond an evaluation harness and a hand-built intent graph. | Decision gates in §12.6 evaluated. |
| **1 — Core, read-mostly, offline (stage 1)** | Per-repo daemon, watcher, store API with the SQLite adapter and an in-memory adapter (§8.2.1), local snapshot and deltas, file ingest, code units as textual anchors with re-anchoring (§8.3), agent-driven intent import (FR-122, FR-124), intent authoring, links and annotations, trace and why queries, MCP adapter, an operations CLI, the spec TUI, minimal registry. Offline mode only (§8.17); local journal and backups; divergence classification for C1, C3, C4 and C7; `resonance status`, `recover` and `eject`; repair lists and lazy agent-driven repair (FR-238, FR-239); invisibility rules (FR-189); `resonance value` (FR-240); offline agent kit for Claude Code (local placement, conventions served over MCP, orientation). Agents edit files directly; no graph-to-disk code writes yet. | S1–S4, S8, S13–S15 pass on a real repository; store conformance suite passes for both adapters. |
| **2 — Git integration, shared (stage 2)** | Committed snapshot and delta log (§8.6.1), open and sealed deltas, file manifests, git monitor, fold and compaction with mechanical repair, merge semantics, conflict nodes, `resonance share` / `unshare`, `.resonance/README.md` for hold-outs, the full divergence classification (§8.18), optional hooks, commit-check report, PR review tooling (FR-066), `resonance check --staged` / `--range`, blocking consistency hooks for Resonance users and agent-side hooks (FR-069, FR-203, FR-215–FR-222), `resonance leave`, FR-012b conflict handling for opted-in users, path scope (FR-178), quiet onboarding with the bootstrap script (§8.21). | S10–S12, S16–S20, S22–S24 pass; two clones on different branches merge cleanly; a hold-out works alongside without installing Resonance. |
| **3 — Verification** | Evidence recording from test runs, link lifecycle automation, stale and orphan reporting, impact queries. | S2 AC1–AC2 and S7 pass with automatic verification. |
| **4 — Graph-to-disk mutations** | Projection writer, self-write suppression, conflict policy, API code mutations. | S9 passes with IDE and build tool noticing changes. |
| **5 — IDE** | IntelliJ plugin (FR-141, FR-142). | Developers can navigate and annotate without the CLI. |
| **6 — Regeneration workflows** | Requirement change drives agent regeneration; `realizes` / `satisfies` links recomputed and re-verified. | S5 and S7 work end to end, with links re-verified automatically. |
| **7 — Enforcement (stage 3)** | `resonance enforce`, CI consistency checks that reject inconsistent pull requests, an exception path, CI bot bookkeeping for non-Resonance pull requests (FR-236), absorbing what slips through (C8), adoption-health reporting across the team. | A team runs at stage 3 with exceptions handled by recovery and bookkeeping, not by reverts. |
| **Track — Graph engine research** | In parallel, from Phase 1 onward: evaluate graph engines (OQ-03) against the store conformance suite and NFR-030–035. Adopting one means a new adapter plus a migration compaction (FR-165). | S21 passes for the chosen engine. |

**Dogfooding** [Decided]: Resonance's own repository, starting with this specification, moves through each stage as soon as that stage is available. Mark and Claude are its first users, so every stage is exercised by a team that is still using git day to day (FR-071).
